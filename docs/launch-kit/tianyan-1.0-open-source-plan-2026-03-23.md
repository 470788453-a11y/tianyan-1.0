# 天衍1.0 开源总方案（GitHub + 传播）

> 目标不是“把所有东西一股脑放上去”，而是把 **天衍1.0** 作为一个可被理解、可被运行、可被讨论、可持续迭代的开源项目推出来，同时让更多人知道“这是你做的”。

## 0. 先说结论

如果你的目标是 **项目影响力 + 个人品牌**，那天衍1.0 的开源打法应该是：

- **先开一个能看懂、能跑起来、能讲清楚的最小可信版本**，不要一次性倒全部历史包袱。
- **先卖定位，再卖代码量**：别人先理解“你在做什么”，才会愿意 star、转发、关注你。
- **先打中文圈，再接 GitHub / X**：你的第一批种子用户更可能来自中文开发者、AI 产品人、独立开发者、创业者。
- **先把你和项目绑定**：不是匿名丢一个仓库，而是明确让外界知道“天衍1.0 是你提出并做出来的系统原型”。

一句话打法：

> **把天衍1.0包装成“一个可运行的人机协作系统原型”，分三周完成：首发建立认知，第二周补可信度，第三周做传播扩散。**

---

## 1. 天衍1.0 是什么，不是什么

### 1.1 它是什么

结合现有材料，天衍1.0 更适合被定义为：

- 一个 **独立于爪云的可运行系统原型**。
- 一个围绕 **人机协作 / 智能体协作流程** 设计的 orchestrator。
- 一个把任务输入、记忆、规划、决策、执行、验证、响应串成主链路的实验型产品。
- 一个已经具备 **TaskCard、状态机、事件总线、子任务队列、验证器、API、简单控制台、文件持久化** 的工程化雏形。
- 一个可以继续往“真实外部 tool adapter / federation / delegation”扩展的基础底座。

更适合对外使用的一句话定位：

> **天衍1.0 是一个把“人机协作工作流”做成可运行系统的开源原型。**

也可以更偏 GitHub 一点：

> **天衍1.0 / AgentX 1.0 is an executable human-agent collaboration system prototype.**

### 1.2 它不是什么

这部分一定要写清楚，不然后面很容易被误解、被喷、被高估。

天衍1.0 现在 **不是**：

- 不是“通用 AGI”。
- 不是“什么都能自动干”的万能体。
- 不是成熟商业 SaaS。
- 不是已经稳定接管复杂生产环境的企业级平台。
- 不是 ClawCloud 的完整开源替代品。
- 不是已经完成多节点协同、外部工具生态、权限治理、插件市场的终极系统。

更实战一点的表达：

> **它是一个已经有骨架、有主链路、有运行面板的系统原型；不是终局产品。**

这个边界感很重要。开源最怕两种死法：

- 一种是太虚，别人看不懂你到底做了什么；
- 另一种是吹太满，别人一跑发现和宣传差太远。

你应该主动占据中间位置：**真东西 + 不吹满**。

## 2. 开源目标：项目影响力 + 个人品牌

这次开源不要只盯着 `star` 数，要同时追两个目标。

### 2.1 项目目标

项目层面的目标是：

- 让别人能快速理解天衍1.0 的问题定义与系统结构。
- 让别人能在本地跑起来，形成第一批真实反馈。
- 让仓库具备持续迭代空间，而不是“一次性上传完就烂尾”。
- 让后续 2.0 / 3.0 / 5.0 的演进有一个公开起点。

### 2.2 个人目标

个人品牌层面的目标是：

- 让别人知道 **这套东西是谁提出、谁设计、谁做出来的**。
- 把你从“会写代码的人”升级成“有系统观点、有产品判断、有工程落地能力的人”。
- 让后续别人提到“人机协作系统 / 智能体工作流 / 中文 AI 原型项目”时，能把你联想到一起。
- 为之后的合作、招聘、咨询、演讲、项目机会打基础。

### 2.3 开源成功不等于什么

你要提前接受一件事：

- 开源成功不等于首周 1 万 star。
- 开源成功也不等于所有人都懂你的系统命名体系。
- 开源成功更现实的定义是：
  - 有人能看懂；
  - 有人能跑通；
  - 有人愿意讨论；
  - 有人开始记住你。

所以，这次不是“押宝爆红”，而是 **搭一条长期有效的公开认知通道**。

## 3. 开源范围：该开哪些，不该开哪些

这是这次最关键的部分。你不是在做数据倾倒，而是在做产品化开源。

### 3.1 第一批建议开源的内容

建议第一批就公开：

#### A. 核心代码骨架

- `src/` 下可运行的服务端主链路。
- orchestrator、planner、decider、verifier、executor 等核心模块。
- TaskCard、状态机、事件总线、队列等基础模型。
- HTTP API 与最小可用的 Web 控制台。

#### B. 必要文档

- `README.md`
- `ARCHITECTURE.md`
- `docs/agentx-1.0-plan.md` 的整理版
- 快速启动文档
- 对外定位文档
- Roadmap
- FAQ

#### C. 示例数据与演示路径

- 最小 demo task
- 任务执行示例截图
- 一组可跑通的 API 示例
- 一份“从输入到输出”的典型执行案例

#### D. 开源基础设施

- `LICENSE`
- `CONTRIBUTING.md`
- `CHANGELOG.md`
- `.env.example`
- Issue / PR templates

### 3.2 第一批不要开源的内容

以下内容建议 **不要** 第一波直接公开：

#### A. 敏感配置

- 真实 `.env`
- API keys
- tokens
- webhook secrets
- 各类账号信息
- 机器路径、服务器地址、内部目录约定

#### B. 历史包袱

- 大量实验中间件
- 已废弃分支的历史输出
- 临时脚本
- 命名混乱、没有解释的旧文档
- 只有你自己看得懂的草稿和思维残留

#### C. 会引起误解的材料

- 尚未验证但写得像“已完成”的功能
- 还没准备公开的路线图细节
- 容易暴露你的真实运维环境、商业线索、内部协作方式的文件
- 过于私人的 memory / notes / receipts

### 3.3 开源切法建议：按“可信最小集”来切

推荐切成三层：

#### 第一层：必须开

- 能证明项目存在且可运行的代码和文档。

#### 第二层：可选补充

- demo、样例、架构图、对比说明、设计 rationale。

#### 第三层：暂不公开

- 历史沉淀、实验残留、敏感资产、未收口设计。

一句话原则：

> **先开“别人能理解并复现价值”的部分，不开“只会增加噪音和风险”的部分。**

## 4. 仓库结构建议

你现在内部保留 `agentx-1.0` 是合理的，但对外要让结构更清楚。

### 4.1 仓库命名建议

优先建议：

- `tianyan-1.0`
- `tianyan-agentx-1.0`
- `agentx-1.0`

如果你想兼顾中文品牌和英文可检索性，建议：

- GitHub 仓库名：`tianyan-1.0`
- README 标题：`天衍1.0 / AgentX 1.0`

这样最平衡。

### 4.2 tagline 建议

可选 tagline：

- 中文：`一个可运行的人机协作系统原型`
- 中文：`把人机协作工作流做成系统，而不是只停留在提示词层`
- 英文：`An executable human-agent collaboration system prototype`
- 英文：`From workflow ideas to a runnable human-agent orchestration system`

### 4.3 推荐目录结构

```text
tianyan-1.0/
├─ src/                    # 核心服务与主链路
├─ web/                    # 简单控制台（如需保留）
├─ docs/
│  ├─ architecture.md
│  ├─ roadmap.md
│  ├─ quickstart.md
│  ├─ faq.md
│  └─ examples/
├─ examples/               # 最小任务样例 / API 调用样例
├─ scripts/                # 启动、构建、检查脚本
├─ tests/                  # Node 内置测试
├─ .data.example/          # 脱敏后的示例数据结构（可选）
├─ .env.example
├─ README.md
├─ ARCHITECTURE.md
├─ CONTRIBUTING.md
├─ CHANGELOG.md
├─ LICENSE
└─ package.json
```

### 4.4 README 首页建议结构

你的 README 不要写成“内部备忘录”，要写成对陌生人的 landing page。

建议结构：

1. 项目一句话定位
2. 它解决什么问题
3. 当前已有能力
4. 5 分钟跑起来
5. 系统主链路图
6. API 示例
7. 截图 / demo gif
8. Roadmap
9. 作者与背景
10. 如何参与

### 4.5 你个人品牌要放在哪里

建议明确写入：

- README 顶部或底部增加 `Author / Maintainer`
- GitHub Profile README 同步挂上项目链接
- 项目发布帖里固定带一句：
  - `这是我做的一个人机协作系统原型，欢迎试用和提意见。`

重点不是“卖人设”，而是 **别让项目和你脱钩**。

## 5. 发布节奏：首发、第二周、第三周

不要一次发布后失联。开源项目的第一印象，很多时候不是首帖，而是 **发布后 14 天有没有持续动作**。

## 5.1 首发周：先建立“看得懂 + 能跑”

首发目标：

- 建立最初认知
- 让人快速判断这项目值不值得看
- 让第一批人能跑起来

首发必须准备好的东西：

- 一个干净的 GitHub 仓库
- 一版清楚的 `README.md`
- 一份架构说明
- 一份 quickstart
- 一条可运行 demo
- 3~5 张截图或 1 个短 gif
- 一篇中文首发介绍文

首发当天建议动作：

- GitHub 发仓库
- README 完整上线
- 打第一个 release tag：`v0.1.0`
- 同步发中文介绍帖
- 同步发一条简洁版 X / GitHub 动态

首发内容重点不是“我做了多少功能”，而是：

- 为什么做这个
- 它的基本结构是什么
- 现在能干什么
- 接下来会补什么

### 5.2 第二周：补可信度

第二周的目标不是再喊一次“我开源了”，而是补充可信度。

建议动作：

- 补一篇《架构拆解》
- 补一篇《一个任务是怎么跑完的》
- 修首周反馈里最明显的问题
- 增加 1~2 个样例任务
- 补 issue 模板和贡献说明
- 如果有人提问，集中回复并整理 FAQ

第二周发声主题建议：

- `这个系统具体怎么流转？`
- `为什么我没有把它做成一个聊天壳，而是做成任务系统？`
- `天衍1.0 当前能跑到哪一步？`

### 5.3 第三周：做扩散，不是做噪音

第三周才更适合做“让别人知道你”。

建议动作：

- 发一篇“开源 2 周后复盘”
- 展示真实反馈、数据、改动
- 公开 roadmap 的下一阶段
- 做一张更容易传播的结构图
- 开始邀请协作者 / 体验者

第三周发声重点：

- 不再只讲“我开源了”
- 而是讲“这个项目在进化，而且背后有明确的人和方法论”

一句话：

> **首发卖认知，第二周卖可信度，第三周卖持续性。**

## 6. 传播渠道与节奏：中文圈优先，兼顾 GitHub / X

你的项目第一波受众，不是硅谷投资人，也不是只看英文的大 V，而是：

- 中文开发者
- AI 产品经理 / 创业者
- 独立开发者
- 关注 Agent / workflow / automation 的人
- 对“把想法做成系统”有兴趣的人

### 6.1 中文圈优先渠道

建议优先顺序：

#### 第一梯队：最适合首发

- 即刻
- 少数派社区 / 个人博客
- 知乎文章
- 掘金
- V2EX（偏谨慎，文案要克制）
- 微信公众号 / 朋友圈
- 技术或 AI 社群

#### 第二梯队：跟进扩散

- Bilibili 短讲解视频
- 小红书（偏产品故事，不要太技术）
- 抖音（如果做成短 demo）

### 6.2 GitHub / X 的角色

- **GitHub** 负责承接：让别人查看代码、star、提 issue、fork。
- **X** 负责跨中文圈外溢：一句话讲清楚项目 + 链接。

不要指望 X 帮你完成首发教育。X 更适合：

- 首发当天发英文简版
- 第二周发架构图
- 第三周发进展更新

### 6.3 推荐传播节奏

#### 首发当天

发三种版本：

- 长文版：中文平台，讲清定位、动机、结构、当前能力
- 短文版：社群 / 朋友圈 / 即刻
- 极短版：X / GitHub 动态

#### 第 3~5 天

- 补一篇“系统架构拆解”
- 回答首批最常见问题

#### 第 7~10 天

- 发“真实任务跑通案例”
- 展示迭代记录

#### 第 14~21 天

- 发复盘
- 发下一阶段路线图
- 邀请协作

### 6.4 文案重点

中文首发文案要尽量围绕三件事：

- 我为什么做这个
- 它和普通聊天机器人有什么不同
- 当前已经做到什么程度

不要把重点写成：

- 一堆抽象概念堆砌
- 一堆版本史
- 一堆宏大叙事

传播上最有效的是：

> **具体问题 + 具体结构 + 真实边界 + 可运行链接**

## 7. 你该怎么讲自己，才不会显得尴尬

如果你想“让别人知道我”，核心不是狂刷存在感，而是让大家自然接受：

- 这是你提出的方向
- 这是你亲手做出来的东西
- 你是一个会做系统的人

### 7.1 对外自我绑定建议

你可以稳定用下面这种话术：

- `这是我最近开源的一个项目：天衍1.0。`
- `我想把“人机协作”从口号做成一个能跑的系统，所以做了这个原型。`
- `现在它还不是终局产品，但已经有任务链路、验证器、API 和控制台。`
- `如果你也在做 agent / workflow / automation，欢迎交流。`

这类表达有几个好处：

- 有主语：是你做的
- 有判断：你为什么做
- 有边界：还不是终局
- 有邀请：欢迎讨论

### 7.2 不建议的表达

尽量别上来就说：

- `我做了一个颠覆性的 AGI 系统`
- `这将重新定义一切`
- `这是全世界最先进的……`

这种说法短期可能吸睛，长期只会让严肃用户直接关掉页面。

你更适合的品牌路径是：

> **清楚、克制、能打。**

## 8. 风险提醒：哪些坑一定别踩

### 8.1 不要开源敏感配置

这个是底线：

- 不上传真实 `.env`
- 不上传 keys / tokens / cookies / webhook secrets
- 不上传包含真实账号、真实路径、真实机器信息的配置
- 不上传可能暴露内部业务逻辑或对外资源入口的文件

上线前建议至少做一次：

- 敏感词扫描
- `.gitignore` 检查
- 示例配置替换
- 历史提交检查

### 8.2 不要一次性倒出全部历史包袱

历史文件越多，不代表越强；很多时候只代表越乱。

不要把这些直接丢出去：

- 旧试验文档
- 中间态 receipts
- 未整理的脚本
- 已废弃命名体系
- 连你自己都解释不清的半成品

开源不是归档硬盘，而是设计公共入口。

### 8.3 不要把内部命名体系原封不动压给外界

内部可以保留 `agentx-1.0`，但对外要尽量做到：

- 名称统一
- 入口统一
- 术语有解释
- 文档别默认别人知道上下文

### 8.4 不要首发后断更

很多项目不是死于代码，而是死于“发布即失踪”。

如果首发后两周没有：

- 回 issue
- 修文档
- 补样例
- 发更新

那外界会默认：这是一次性冲动项目。

### 8.5 不要把开源目标搞成“求赞”

真正有效的动作不是求转发，而是：

- 让别人更容易理解
- 让别人更容易运行
- 让别人更容易讨论

影响力是结果，不是按钮。

## 10. 一个更稳的实际执行方案

如果你现在就开始做，我建议按下面这条线执行。

### 阶段 A：先整理成“能见人”的公开版本

重点：

- 清 README
- 清目录
- 清配置
- 清掉不该公开的文件
- 准备 demo

### 阶段 B：发第一版 GitHub

重点：

- 发仓库
- 打 tag
- 写 release
- 确保能 clone、能 install、能 run

### 阶段 C：同步中文首发

重点：

- 讲定位
- 讲问题意识
- 讲当前能力
- 放仓库链接

### 阶段 D：两周内连续补动作

重点：

- 文档补丁
- 示例补丁
- 回答问题
- 继续发进展

这个顺序的好处是：

- 先保底质量
- 再对外曝光
- 再借反馈迭代

而不是“先发出去，后面再补洞”。

## 11. 立即执行的 7 步动作清单

下面这 7 步，就是你现在可以直接照着做的版本。

### 1）确定公开名称和口径

定死：

- 对外名：`天衍1.0 / AgentX 1.0`
- 一句话定位：`一个可运行的人机协作系统原型`
- 边界口径：`不是 AGI，不是成熟商业产品`

### 2）清点仓库，只保留“可信最小集”

保留：

- 核心代码
- 必要文档
- demo
- 测试
- 示例配置

移除或暂存：

- 敏感配置
- 历史包袱
- 临时脚本
- 私人记录
- 未验证功能

### 3）重写 README 首页

确保 README 第一屏就说清：

- 它是什么
- 能做什么
- 怎么跑
- 作者是谁
- 下一步是什么

### 4）补齐开源必需文件

至少补齐：

- `LICENSE`
- `CONTRIBUTING.md`
- `CHANGELOG.md`
- `.env.example`
- issue / PR 模板

### 5）做一个可演示的最小 demo

要求不是炫，而是稳：

- 本地能跑
- 有截图
- 有 API 示例
- 最好有一个 30~60 秒录屏

### 6）首发到 GitHub，并打 `v0.1.0`

发布时同步准备：

- 仓库说明
- release note
- 标签
- 首页截图

### 7）在中文圈发第一波，并在 14 天内持续更新

第一波优先发：

- 即刻 / 知乎 / 掘金 / 社群 / 朋友圈
- GitHub 动态
- X 简版

然后两周内至少补两次更新：

- 一次讲架构
- 一次讲进展 / 反馈 / 下一步

## 12. 最后一句判断

如果你真想通过开源让别人知道你，最优路径不是“显得厉害”，而是：

> **把天衍1.0 做成一个别人一看就知道你有判断力、一跑就知道你有工程能力、跟两周就知道你不是一时兴起的项目。**

这才是对项目和你本人都更值钱的开源方式。
